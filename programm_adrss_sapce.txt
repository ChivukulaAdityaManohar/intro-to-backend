1. Program Address Space in C++
When a C++ program runs, the operating system gives it a virtual address space — a range of memory addresses the program can use.
This space is divided into logical segments (not always physically separate, but conceptually distinct):
+---------------------------+  High addresses
| Command-line args, env    |  (part of stack area)
+---------------------------+
| Stack                     |  Local variables, function calls
+---------------------------+
| Heap                      |  Dynamic allocations (new/malloc)
+---------------------------+
| BSS Segment  (Block Started by Symbol)              |  Uninitialized global/static vars
+---------------------------+
| Data Segment (.data)      |  Initialized global/static vars
+---------------------------+
| Read-only Data (.rodata)  |  const globals, string literals
+---------------------------+
| Text Segment (.text)      |  Executable code (machine instructions)
+---------------------------+  Low addresses




In C++, semantics refers to the meaning or behavior of a piece of code — what it does when it runs — as opposed to syntax, which is about the rules for writing the code correctly.

Key Points about Semantics in C++


Meaning of Code

Semantics defines how the compiler and runtime interpret your code.
Example:Cppint x = 5;  
x = x + 2;


Syntax: The code follows C++ grammar rules.
Semantics: The variable x now holds the value 7.





Types of Semantics

Static semantics: Rules checked at compile time (e.g., type compatibility, variable scope).
Dynamic semantics: Behavior observed at runtime (e.g., actual values, memory allocation, side effects).



Examples in C++

Syntax correct but semantically wrong:Cppint a = 5 / 0; // ✅ Syntax OK, ❌ Semantics: division by zero → runtime error


Operator overloading semantics:Cppclass Vector {
public:
    int x, y;
    Vector(int a, int b) : x(a), y(b) {}
    Vector operator+(const Vector& v) {
        return Vector(x + v.x, y + v.y);
    }
};


The + operator’s syntax is fixed, but its semantics here mean “add two vectors.”





Why Semantics Matter

Two programs can have identical syntax but different semantics depending on:

Variable types
Operator overloads
Function implementations
Control flow logic






✅ In short:

Syntax = How you write it (grammar).
Semantics = What it means / does (behavior).

2. Data Segment


What it is:
A section of memory that stores global and static variables that are initialized before program execution starts.


Examples:


Cppint g1 = 42;        // in data segment
static int s1 = 5;  // in data segment


Properties:

Lifetime: Entire program run.
Writable: Yes (unless declared const).
Location: .data section in the executable.




3. Read-Only Data Segment (.rodata)


What it is:
A section of memory that stores immutable data — data that should not be modified at runtime.


Examples:


Cppconst int g2 = 100;       // in .rodata
const char* msg = "Hi!";  // string literal in .rodata


Properties:

Lifetime: Entire program run.
Writable: No — OS marks it read-only; writing causes a segmentation fault.
Location: .rodata section in the executable.




4. Why Separate .data and .rodata?

Security: Prevents accidental or malicious modification of constants.
Optimization: Read-only data can be shared between processes.
Memory Protection: OS can mark .rodata as non-writable.


5. Quick Demo Program
Here’s a C++ program that shows where different variables live in memory:
Cpp#include <iostream>
using namespace std;

int g_init = 10;           // data segment
int g_uninit;              // BSS segment
const int g_const = 20;    // read-only data segment

int main() {
    int local_var = 30;    // stack
    static int s_var = 40; // data segment
    const char* str = "Hello"; // str pointer on stack, literal in .rodata
    int* heap_var = new int(50); // heap

    cout << "Address of g_init   (data)     : " << &g_init << endl;
    cout << "Address of g_uninit (BSS)      : " << &g_uninit << endl;
    cout << "Address of g_const  (.rodata)  : " << &g_const << endl;
    cout << "Address of local_var(stack)    : " << &local_var << endl;
    cout << "Address of s_var    (data)     : " << &s_var << endl;
    cout << "Address of str ptr  (stack)    : " << &str << endl;
    cout << "Address of literal  (.rodata)  : " << static_cast<const void*>(str) << endl;
    cout << "Address of heap_var (heap)     : " << heap_var << endl;

    delete heap_var;
    return 0;
}


Sample Output (addresses will vary)
Address of g_init   (data)     : 0x60104c
Address of g_uninit (BSS)      : 0x601048
Address of g_const  (.rodata)  : 0x4006d0
Address of local_var(stack)    : 0x7ffd5b3c8a4c
Address of s_var    (data)     : 0x601044
Address of str ptr  (stack)    : 0x7ffd5b3c8a40
Address of literal  (.rodata)  : 0x4006e4
Address of heap_var (heap)     : 0x1c3c010


💡 Key takeaway:

Data segment = writable, initialized globals/statics.
Read-only data segment = immutable constants, string literals.
Both are part of the program’s address space, which also includes stack, heap, BSS, and text/code.

Design patterns in C++ are proven, reusable solutions to common software design problems.
They are not code you copy-paste, but templates for solving recurring problems in a structured way.
Design patterns are generally classified into three main categories:

1. Creational Patterns
Focus on object creation mechanisms to make the system independent of how objects are created.
a) Singleton Pattern
Ensures only one instance of a class exists and provides a global access point.
Cpp#include <iostream>
#include <mutex>

class Singleton {
private:
    static Singleton* instance;
    static std::mutex mtx;

    // Private constructor to prevent direct instantiation
    Singleton() { std::cout << "Singleton instance created.\n"; }

public:
    // Delete copy constructor and assignment operator
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;

    static Singleton* getInstance() {
        std::lock_guard<std::mutex> lock(mtx);
        if (!instance) {
            instance = new Singleton();
        }
        return instance;
    }

    void showMessage() {
        std::cout << "Hello from Singleton!\n";
    }
};

// Initialize static members
Singleton* Singleton::instance = nullptr;
std::mutex Singleton::mtx;

int main() {
    Singleton::getInstance()->showMessage();
    return 0;
}


b) Factory Method Pattern
Defines an interface for creating objects but lets subclasses decide which class to instantiate.
Cpp#include <iostream>
#include <memory>

// Product interface
class Shape {
public:
    virtual void draw() = 0;
    virtual ~Shape() = default;
};

// Concrete products
class Circle : public Shape {
public:
    void draw() override { std::cout << "Drawing Circle\n"; }
};

class Square : public Shape {
public:
    void draw() override { std::cout << "Drawing Square\n"; }
};

// Factory
class ShapeFactory {
public:
    static std::unique_ptr<Shape> createShape(const std::string& type) {
        if (type == "circle") return std::make_unique<Circle>();
        if (type == "square") return std::make_unique<Square>();
        return nullptr;
    }
};

int main() {
    auto shape = ShapeFactory::createShape("circle");
    if (shape) shape->draw();
    return 0;
}


2. Structural Patterns
Deal with object composition to form larger structures.
a) Adapter Pattern
Allows incompatible interfaces to work together.
Cpp#include <iostream>

// Old interface
class OldPrinter {
public:
    void oldPrint() { std::cout << "Printing using old printer\n"; }
};

// New interface
class NewPrinter {
public:
    virtual void print() = 0;
};

// Adapter
class PrinterAdapter : public NewPrinter {
private:
    OldPrinter* oldPrinter;
public:
    PrinterAdapter(OldPrinter* op) : oldPrinter(op) {}
    void print() override { oldPrinter->oldPrint(); }
};

int main() {
    OldPrinter oldPrinter;
    PrinterAdapter adapter(&oldPrinter);
    adapter.print();
    return 0;
}


3. Behavioral Patterns
Focus on communication between objects.
a) Observer Pattern
Defines a one-to-many dependency so that when one object changes state, all dependents are notified.
Cpp#include <iostream>
#include <vector>
#include <string>

// Observer interface
class Observer {
public:
    virtual void update(const std::string& message) = 0;
};

// Subject
class Subject {
private:
    std::vector<Observer*> observers;
public:
    void attach(Observer* obs) { observers.push_back(obs); }
    void notify(const std::string& message) {
        for (auto obs : observers) obs->update(message);
    }
};

// Concrete Observer
class ConcreteObserver : public Observer {
private:
    std::string name;
public:
    ConcreteObserver(std::string n) : name(n) {}
    void update(const std::string& message) override {
        std::cout << name << " received: " << message << "\n";
    }
};

int main() {
    Subject subject;
    ConcreteObserver obs1("Observer1"), obs2("Observer2");

    subject.attach(&obs1);
    subject.attach(&obs2);

    subject.notify("Event happened!");
    return 0;
}
